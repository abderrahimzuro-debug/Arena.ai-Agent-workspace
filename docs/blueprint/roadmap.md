# خارطة التنفيذ ومعايير القبول

## مبدأ التنفيذ

ابدأ بنواة صغيرة قابلة للاختبار. لا تبدأ بتعدد الوكلاء الكامل أو عشرات المزودين قبل إثبات دورة عمل واحدة آمنة وناجحة.

## المرحلة 0 — تثبيت المتطلبات والقرارات
- اعتماد إطار سطح المكتب واللغة بعد نموذج تقني.
- تحديد أنظمة Windows المدعومة.
- تحديد سياسة الترخيص والتوزيع.
- التحقق من مزود واحد ونموذج واحد.
- إعداد CI وفحوص الجودة.

**القبول:** قرارات موثقة، تطبيق تجريبي يفتح على Windows، وبناء قابل للتكرار.

## المرحلة 1 — النواة المحلية
- واجهة محادثة ومجلد مشروع.
- File Explorer ومحرر كود.
- SQLite للمحادثات والإعدادات.
- Secret Store للنموذج الأول.
- Workspace Engine لقراءة الملفات وكتابة patches.
- Diff وcheckpoint وUndo.
- Permission Engine بوضع الموافقة.

**القبول:** يختار المستخدم مشروعًا، ويقرأ ملفًا، ويطلب تعديلًا، ويراجع diff، ويقبل أو يرفض دون وصول خارج المجلد المصرح.

## المرحلة 2 — موصل AI واحد ثم كتالوج متعدد
- Provider Adapter موحد.
- بث الردود وتسجيل Usage.
- Model Catalog مع القدرات والسياق.
- معالجة أخطاء المصادقة والحصة والحد المؤقت.
- إعداد Reasoning mapping إن كان مدعومًا.

**القبول:** يمكن استبدال المزود دون تعديل الواجهة أو Core، وتظهر بيانات الاستهلاك المتاحة.

## المرحلة 3 — Context & Memory
- فهرسة الملفات والرموز.
- Project Memory وTask Memory وWorking Context.
- استرجاع مقتطفات ذات صلة.
- تلخيص المحادثات الطويلة.
- Local Result Cache مع إبطال صحيح.
- Prompt caching فقط عند دعم المزود وتوثيق أثره.

**القبول:** لا يرسل التطبيق كامل المشروع افتراضيًا، وتبقى المراجع متسقة بعد تعديل الملفات.

## المرحلة 4 — أدوات البحث والمهارات
- Web Research Engine نصي مع مصادر.
- Skills Manager بصيغة Agent Skills.
- أدوات الاختبار وlint.
- MCP اختياري مع فحص وصلاحيات.

**القبول:** تظهر مصادر البحث، ولا تنفذ مهارة أو أداة خارجية دون سياسة تثبيت/موافقة.

## المرحلة 5 — Orchestrator والوكلاء
- تخطيط المهام وتقسيمها.
- وكيل رئيسي ووكلاء متخصصون.
- Shared Project State.
- إدارة تعارضات الملفات.
- مراجعة ودمج نتائج الوكلاء.

**القبول:** تنفيذ مهام مستقلة ومنع الكتابة المتزامنة المتعارضة وتسجيل التغييرات.

## المرحلة 6 — التوجيه والتقييم والتبديل
- Model Router متعدد المزودين.
- Model Evaluator حسب فئة المهمة.
- تقييم المستخدم والاختبارات الموضوعية.
- Fallback واعٍ بنوع الخطأ.
- Auto Reasoning وقياس الجودة/الزمن/الاستهلاك.

**القبول:** لا يحدث fallback عند خطأ مفتاح أو شبكة بصورة عمياء؛ ولا يصنف نموذج كأفضل دون عينة كافية وحديثة.

## المرحلة 7 — GitHub والمزامنة والتهيئة
- Git status/diff/branch/commit.
- clone/pull/push بموافقة.
- GitHub API/PR بعد اكتمال المصادقة الآمنة.
- نسخ احتياطي اختياري منفصل للمحادثات.
- مثبت Windows وتحديثات وتوثيق المستخدم.

**القبول:** لا ترفع الأسرار أو المحادثات افتراضيًا، ويستطيع المستخدم مراجعة كل تغيير قبل Push.

## اختبارات غير قابلة للتفاوض

- Unit tests لكل Permission Policy.
- اختبارات منع path traversal.
- اختبارات عدم تسريب الأسرار في logs.
- اختبار تعارض تعديلات ملف واحد.
- اختبار انقطاع الشبكة ونفاد الحصة.
- اختبار حدود السياق ومخرجات ضخمة.
- اختبار إعادة بناء الفهرس.
- اختبارات Windows على بيئة جديدة.
- Evals تقيس نجاح المهمة وجودة التعديل لا عدد التوكنات فقط.

## معيار نجاح المنتج

**Cost per Successfully Completed Task:** الاستهلاك اللازم لإكمال مهمة بنجاح، مع تسجيل الجودة وعدد المحاولات والزمن والأخطاء. انخفاض التوكنات وحده ليس نجاحًا إذا زادت الإخفاقات أو إعادة العمل.
