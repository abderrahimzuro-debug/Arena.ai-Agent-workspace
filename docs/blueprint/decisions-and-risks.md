## مسائل تحتاج حسمًا قبل التنفيذ

1. اختيار Tauri أم Electron بعد اختبار حجم التطبيق وتجربة Windows.
2. لغة Backend النهائية (Rust أو .NET أو Node) وفق متطلبات الأدوات.
3. هل يبدأ التطبيق بمزود واحد أم اثنين لإثبات الـ Adapter؟
4. الحد الأدنى لمواصفات الجهاز.
5. سياسة تشغيل أوامر الطرفية والعزل.
6. حدود النسخ الاحتياطي والتشفير والمزامنة.
7. مزود البحث الأفضل من حيث المجانية والجودة والخصوصية.
8. مهارات البداية التي تم فحص تراخيصها ومحتواها.
9. طريقة حساب درجات تقييم النماذج ومنع العينات القليلة من تضليل Router.
10. سياسة تحديث قائمة النماذج والحصص تلقائيًا.

## مخاطر رئيسية وتخفيفها

| الخطر | الأثر | التخفيف |
|---|---|---|
| تغير الخطط المجانية | تعطل مزود أو استهلاك غير متوقع | تحقق دوري وتاريخ تحقق وبدائل |
| تسريب API keys | اختراق حساب المستخدم | OS Credential Vault وحجب السجلات |
| Prompt Injection | تنفيذ أوامر غير آمنة | فصل البيانات عن التعليمات وصلاحيات خارج النموذج |
| تعديل متزامن | فساد ملفات أو فقد تغييرات | أقفال/فروع/worktrees ودمج بمراجعة |
| Context bloat | استهلاك مرتفع | فهرسة واسترجاع مقتطفات وذاكرة هرمية |
| Cache stale | نتائج خاطئة | مفاتيح cache تشمل hash المدخلات وإبطال دقيق |
| Fallback خاطئ | استهلاك وتكرار طلبات | تصنيف الأخطاء وسياسة إعادة المحاولة |
| تقييم متحيز | اختيار نموذج غير مناسب | اختبارات معيارية وعينات كافية وقياس حديث |
| مهارات أو MCP خبيثة | تنفيذ شيفرة أو تسريب بيانات | مصدر موثوق وفحص وموافقة وعزل |
| تضخم الإصدار الأول | تأخر المشروع | مراحل واضحة وMVP صغير |

## سياسة التحقق من المعلومات المتغيرة

قبل اعتماد مزود أو نموذج أو مكتبة:
- افتح الوثائق الرسمية وصفحة الأسعار/الحصص.
- سجل رابط المصدر وتاريخ التحقق.
- اختبر API فعليًا في بيئة تجريبية.
- لا تعتمد على منشورات قديمة أو قوائم مجتمعية كمرجع وحيد.
- أعد التحقق قبل كل إصدار رئيسي.

## تعريف الإنجاز

لا تعتبر ميزة مكتملة لمجرد ظهور زر لها. يجب أن يكون لها عقد واجهة موثق، وسياسة صلاحيات، ومعالجة أخطاء، واختبارات، وسجلات لا تكشف أسرارًا، وتوثيق استخدام، ومعيار قبول قابل للتحقق.
